# Design Review Skill 设计规范

> 创建日期: 2026-04-10

## 一、概述

### 1.1 目的

设计一套结构化的评审流程模板，用于系统化检查模块设计文档的完整性和一致性。

### 1.2 适用范围

| 项目 | 说明 |
|------|------|
| 适用文档 | 模块详细设计文档（如调度服务模块、执行服务模块） |
| 执行方式 | Claude Code Skill，由 Claude 或人工按步骤执行 |
| 输出形式 | 分类问题清单，按维度分组，标注位置引用 |

### 1.3 核心特性

- **单文档自检为主**：聚焦单个设计文档内部的完整性和一致性
- **穿透验证支持**：检查跨文档引用和依赖组件源码的真实性
- **混合判定模式**：完整性、一致性检查采用规则级（自动判定），合理性检查采用原则级（主观判定）

## 二、检查维度

### 2.1 维度分类

| 维度 | 检查目标 | 判定模式 | 问题数量（示例） |
|------|----------|----------|------------------|
| 结构完整性 | 文档章节结构是否完整 | 规则级 | 3项 |
| 定义完整性 | 每个定义元素是否完整 | 规则级 | 5项 |
| 术语一致性 | 术语、命名是否统一 | 规则级 | 3项 |
| 逻辑一致性 | 流程、状态流转是否自洽 | 规则级 | 4项 |
| 接口一致性 | 跨文档/跨组件接口是否匹配 | 规则级 | 4项 |
| 设计合理性 | 架构、职责、流程是否合理 | 原则级 | 6项 |

### 2.2 判定模式说明

**规则级**：
- 有明确的匹配规则和判定标准
- 结果为「通过」或「失败」
- 可自动执行，无需主观判断

**原则级**：
- 基于设计原则进行评估
- 结果为「通过」或「警告」（非强制性）
- 需要评审者根据上下文判断

## 三、检查项定义

### 3.1 结构完整性（规则级）

| 检查项ID | 检查项名称 | 匹配规则 | 判定标准 |
|----------|------------|----------|----------|
| S-001 | 必要章节完整 | 检查是否存在概述、详细设计章节 | 缺少任意必要章节 → 失败 |
| S-002 | 模块简介完整 | 每个内部模块是否有职责说明和方法签名表 | 模块缺少职责说明或方法签名表 → 失败 |
| S-003 | 流程图完整 | 关键流程是否有时序图/流程图 | 涉及多模块协作的流程缺少图示 → 失败 |

**必要章节定义**：
- 概述章节：包含文档目的、模块架构图、职责边界表
- 详细设计章节：包含数据结构定义、API接口定义

**关键流程定义**：
- 涉及3个及以上模块协作的流程
- 核心业务流程（如任务创建、状态上报）

### 3.2 定义完整性（规则级）

| 检查项ID | 检查项名称 | 匹配规则 | 判定标准 |
|----------|------------|----------|----------|
| D-001 | 数据结构字段完整 | 表格中每行是否有类型、说明列 | 存在字段缺少类型或说明 → 失败 |
| D-002 | 方法签名完整 | 方法是否有参数类型、返回值类型 | 方法缺少参数类型或返回值 → 失败 |
| D-003 | 状态枚举完整 | 状态枚举是否有值和说明列 | 状态枚举缺少值或说明 → 失败 |
| D-004 | 接口定义完整 | 接口是否有路径、方法、请求/响应结构 | 接口缺少路径或响应结构 → 失败 |
| D-005 | 配置参数完整 | 配置表是否有类型、默认值、说明 | 配置参数缺少默认值或说明 → 失败 |

**表格格式识别**：
- 数据结构表格：字段名 | 类型 | 必填 | 说明 | 约束（可选）
- 方法签名表格：方法 | 说明 | 关键程度（可选）
- 配置参数表格：参数名 | 类型 | 默认值 | 说明

### 3.3 术语一致性（规则级）

| 检查项ID | 检查项名称 | 匹配规则 | 判定标准 |
|----------|------------|----------|----------|
| T-001 | 术语命名统一 | 同一概念在不同位置是否使用相同名称 | 同一概念使用不同名称 → 失败 |
| T-002 | 命名风格统一 | 是否混用 snake_case 和 camelCase | 同类元素命名风格不一致 → 失败 |
| T-003 | 状态名称统一 | 状态名称与枚举值是否匹配 | 状态枚举值与文字描述不一致 → 失败 |

**常见术语不一致示例**：
- task_id 与 TaskId 混用
- SubTask 与 sub_task 混用
- status 与 Status 混用

### 3.4 逻辑一致性（规则级）

| 检查项ID | 检查项名称 | 匹配规则 | 判定标准 |
|----------|------------|----------|----------|
| L-001 | 状态流转完整 | 流程图/时序图中的状态是否都在枚举中定义 | 流程图出现未定义状态 → 失败 |
| L-002 | 流程节点匹配 | 时序图参与者是否与模块定义对应 | 出现未定义的模块参与者 → 失败 |
| L-003 | 依赖方向正确 | 依赖关系图是否与职责边界表匹配 | 依赖关系与职责表矛盾 → 失败 |
| L-004 | 方法调用匹配 | 流程中调用的方法是否在方法签名表中定义 | 流程调用未定义的方法 → 失败 |

**提取规则**：
- 从 mermaid 时序图提取参与者名称
- 从 mermaid 流程图提取状态节点
- 从流程描述提取方法调用

### 3.5 接口一致性（规则级）

| 检查项ID | 检查项名称 | 匹配规则 | 判定标准 |
|----------|------------|----------|----------|
| I-001 | 数据结构字段匹配 | 引用的数据结构与定义文档一致 | 字段名称或类型不一致 → 失败 |
| I-002 | 外部接口存在 | 声称调用的外部接口在依赖文档/源码中存在 | 接口不存在 → 失败 |
| I-003 | 请求响应结构匹配 | 跨文档引用的请求响应结构一致 | 字段缺失或类型不同 → 失败 |
| I-004 | 枚举值匹配 | 跨文档引用的状态枚举一致 | 枚举值或名称不同 → 失败 |

**穿透验证范围**：
- 跨文档：docs/designs/ 目录下的其他设计文档
- 依赖文档：docs/dependencies/ 目录下的接口文档
- 依赖源码：AgentCube SDK、eval-data 等外部项目

### 3.6 设计合理性（原则级）

| 检查项ID | 检查项名称 | 检查原则 | 典型问题示例 |
|----------|------------|----------|--------------|
| R-001 | 职责划分清晰 | 每个模块是否有单一明确的职责 | 一个模块承担过多职责 → 警告 |
| R-002 | 依赖方向合理 | 是否存在下层依赖上层、循环依赖 | Storage 层依赖 TaskManager → 警告 |
| R-003 | 错误处理覆盖 | 关键流程是否有错误处理说明 | 核心流程缺少失败处理分支 → 警告 |
| R-004 | 并发安全设计 | 并发场景是否有同步机制说明 | 共享资源无同步机制 → 警告 |
| R-005 | 失败恢复策略 | 是否有失败重试和恢复机制 | 失败后无重试或恢复说明 → 警告 |
| R-006 | 可观测性设计 | 是否有日志、监控指标定义 | 缺少关键操作的可观测性说明 → 警告 |

**评估依据**：
- 模块职责边界表是否清晰定义「负责」和「不负责」
- 依赖关系图是否遵循单向依赖原则
- 关键流程是否有异常分支说明
- 并发相关代码是否有同步说明

## 四、执行流程

### 4.1 流程步骤

```
步骤1: 解析文档
       ↓ 提取定义元素（数据结构、方法、状态、接口、流程图）
步骤2: 结构完整性检查
       ↓ 规则级自动判定
步骤3: 定义完整性检查
       ↓ 规则级自动判定
步骤4: 术语一致性检查
       ↓ 规则级自动判定
步骤5: 逻辑一致性检查
       ↓ 规则级自动判定
步骤6: 接口一致性检查
       ↓ 穿透到跨文档/源码验证
步骤7: 设计合理性检查
       ↓ 原则级主观判定
步骤8: 输出问题清单
       ↓ 按维度分组，标注位置引用
```

### 4.2 文档解析规则

**提取目标**：

| 元素类型 | 提取规则 | 存储结构 |
|----------|----------|----------|
| 数据结构 | 匹配「字段名 | 类型」表格 | `{name, fields: [{name, type, required, desc}]}` |
| 方法签名 | 匹配代码块中的 `func` 定义或方法签名表 | `{name, params, returns}` |
| 状态枚举 | 匹配「值 | 名称 | 说明」表格 | `{name, values: [{value, name, desc}]}` |
| 接口定义 | 匹配「路径 | 方法」表格 | `{path, method, request, response}` |
| 流程图 | 解析 mermaid 代码块 | `{type, participants, states}` |

### 4.3 穿透验证规则

**跨文档验证**：
1. 从当前文档提取引用的外部数据结构/接口名称
2. 定位到对应的设计文档（如 docs/designs/数据模型详细设计文档.md）
3. 比对字段名称、类型是否一致

**依赖源码验证**：
1. 从当前文档提取声称调用的外部接口/方法
2. 定位到依赖源码目录（如 /home/xmq/projects/go/AgentCube/go-sdk）
3. 使用 Grep 搜索方法定义，确认是否存在
