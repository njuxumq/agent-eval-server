# 模型评测服务设计文档

> 来源：`/home/xmq/projects/go/eval-server`

## 一、概述

### 1.1 背景

当前评测工具只能先下载安装至本地，然后通过shell命令执行的方式使用：

```bash
evidently run --config ./path/to/template/template.yaml \
              --dataset ./path/to/dataset/dataset.xlsx \
              --output ./path/to/result/result.xlsx
```

为更好与MaaS模型评测平台集成，评测工具需支持服务化部署，并提供API接口以便调用。

### 1.2 架构总览

模型评测系统采用双服务架构：

```
┌─────────────────────────────────────────────────────────────────┐
│                        eval-server (调度服务)                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────┐ │
│  │ API层    │→│ Scheduler│→│ EventBus │→│ Client   │→│ MQ     │ │
│  │(Gin)     │ │ Manager  │ │          │ │ Manager  │ │(Pulsar)│ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └────────┘ │
│       ↓            ↓            ↓            ↓                   │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────────────┐ │
│  │ Storage  │ │ Coordinator│ │ Quota   │ │ MongoDB              │ │
│  │(MongoDB) │ │           │ │ Allocator│ │(Task/SubTask/Resource)│ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 任务分配
┌─────────────────────────────────────────────────────────────────┐
│                        eval-engine (执行服务)                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                         │
│  │ API层    │ │ Slot     │ │ Task     │                         │
│  │(Gin)     │ │ Manager  │ │ Tracker  │                         │
│  └──────────┘ └──────────┘ └──────────┘                         │
│       ↓            ↓            ↓                                │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────────────────────┐ │
│  │ Storage  │ │ Slot池   │ │ Shell执行环境                     │ │
│  │(MongoDB) │ │(Linux用户)│ │(evidently评测工具)                │ │
│  └──────────┘ └──────────┘ └──────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

## 二、核心设计

### 2.1 任务模型

#### 任务状态

| 状态值 | 状态名 | 说明 |
|-------|--------|------|
| 0 | WAITING | 等待中 |
| 1 | RUNNING | 执行中 |
| 2 | FINISHED | 执行完成 |
| 3 | FAILED | 任务失败 |
| 4 | CANCELED | 任务取消 |
| 5 | EXCEPTION | 任务异常（中间态，对外展示为RUNNING） |

**状态流转**：

```
WAITING → RUNNING → FINISHED
                 ↘ FAILED
                 ↘ CANCELED
                 ↘ EXCEPTION → RUNNING/FAILED
```

#### 子任务状态

| 状态值 | 状态名 | 说明 |
|-------|--------|------|
| 0 | SubTaskWaiting | 待处理 |
| 1 | SubTaskAllocated | 路数已分配 |
| 2 | SubTaskRunning | 运行中 |
| 3 | SubTaskFinished | 完成 |
| 4 | SubTaskFailed | 失败 |
| 5 | SubTaskException | 异常（可重试） |
| 6 | SubTaskCanceled | 取消 |

#### 子任务类型

| 类型 | 说明 |
|-----|------|
| subj_assessment | 主观评测子任务，需评委模型评分 |
| obj_assessment | 客观评测子任务，自动评分 |
| collection | 汇总子任务，最后执行 |

### 2.2 核心流程

#### 任务提交流程

1. API接收任务提交请求
2. MongoDB保存任务记录
3. Pulsar发布任务消息
4. 返回任务ID给用户

#### 任务调度流程

1. 调度服务订阅Pulsar消息，获取任务标识
2. 将任务送至**模型资源等待队列**
3. 并发控制线程检查模型路数，若足够则送至**待执行任务队列**
4. 任务提交线程查询执行服务槽位使用率
5. 选择使用率最低的执行服务，提交子任务
6. 启动状态轮询线程，监控任务执行

#### 子任务执行流程

1. 执行服务接收子任务提交请求
2. 槽位管理器分配空闲槽位（Linux用户）
3. 写入配置文件到槽位目录
4. 异步执行Shell命令
5. 轮询检查执行状态
6. 执行完成后读取输出文件
7. 上报执行结果
8. 回收槽位

#### 结果汇总流程

1. 所有子任务完成后，调度服务创建汇总子任务
2. 汇总子任务收集所有评测记录
3. 生成评测报告
4. 更新任务状态为FINISHED

### 2.3 调度服务

#### 任务管理器 (TaskManager)

**职责**：
- 任务创建、查询、更新、删除
- 任务状态流转控制
- 任务事件发布

**关键方法**：
- `CreateTask()` - 创建任务
- `UpdateTaskStatus()` - 更新任务状态
- `GetTask()` - 查询任务

#### 子任务拆分器 (SubTaskSplitter)

**职责**：根据任务配置拆分子任务

**拆分逻辑**：
1. 遍历评测维度配置
2. 主观评测 → 创建 subj_assessment 子任务
3. 客观评测 → 创建 obj_assessment 子任务
4. 所有评测完成后 → 创建 collection 子任务

#### 配额分配器 (QuotaAllocator)

**职责**：管理评委模型的并发路数

**分配逻辑**：
1. 任务提交时声明所需模型路数
2. 分配前检查模型剩余路数
3. 分配成功后扣减路数
4. 任务完成后释放路数

**关键约束**：
- 路数请求不能超过模型最大可用路数
- 路数不足时任务进入等待队列

#### 槽位分配器 (SlotAllocator)

**职责**：选择执行服务并分配执行槽位

**分配逻辑**：
1. 定时查询各执行服务的槽位使用率
2. 选择使用率最低的执行服务
3. 调用执行服务的任务提交接口

#### 执行引擎管理器 (EngineManager)

**职责**：管理与执行服务的连接

**核心功能**：
- 执行服务注册与发现
- 心跳检测（定期调用状态查询接口）
- 失联检测（连续多次心跳失败则标记失联）

### 2.4 执行服务

#### 槽位管理器 (SlotManager)

**职责**：管理隔离的执行环境

**槽位创建**：
1. 调用系统函数创建Linux用户
2. 初始化用户目录环境
3. 记录槽位状态

**环境隔离**：
- 每个槽位对应独立的Linux用户
- 任务文件存储在用户目录下
- 进程以该用户身份运行

**槽位回收**：
1. 检查任务执行完成
2. 清理用户目录下的任务文件
3. 标记槽位为空闲

#### 异步任务管理器 (AsyncTaskManager)

**职责**：异步执行任务并管理状态

**执行流程**：
1. 接收任务提交请求
2. 分配槽位
3. 写入配置文件
4. 启动协程执行Shell命令
5. 启动轮询线程检查状态
6. 执行完成后读取输出文件
7. 解析结果并上报

**长时任务管控**：
- 超出最长运行时间的任务强制终止

#### 结果处理

**输出文件约定**：任务输出写入 `./output.json`

**结果解析**：
- 读取 output.json 文件
- 解析 progress、success、message、report_url 等字段
- 上报至数据库

## 三、可靠性设计

### 3.1 失败重试机制

#### 重试场景

| 场景 | 触发条件 | 处理方式 |
|-----|---------|---------|
| Shell异常退出 | exit_code != 0 | 重新调度执行 |
| 输出文件缺失 | 未按约定输出结果 | 重新调度执行 |
| 执行服务失联 | 连续心跳失败 | 重新调度至其他执行服务 |

#### 不重试场景

| 场景 | 处理方式 |
|-----|---------|
| Shell正常退出但评测失败 | 直接标记失败 |
| 任务配置错误 | 直接标记失败 |
| 路数分配超限次数 | 直接标记失败 |
| 槽位分配超限次数 | 直接标记失败 |

#### 重试流程

1. 检测到异常状态
2. 更新子任务状态为 SubTaskException
3. 任务重新送入待执行队列（跳过路数分配）
4. 选择其他执行服务重新执行
5. 达到最大重试次数后标记失败

### 3.2 组件崩溃处理

#### 执行服务失联

**检测方式**：调度服务定期调用执行服务的状态查询接口，连续多次失败则标记失联

**处理流程**：
1. 标记执行服务失联
2. 查询该服务上的所有运行中任务
3. 将任务重新调度至其他执行服务
4. 更新任务记录中的执行服务IP

**影响范围**：重调度的任务会重新消耗Token，已执行的用例会重新执行

#### 调度服务崩溃

**恢复机制**：Pulsar消息队列会在调度服务重启后重新投递未ACK的消息

**恢复流程**：
1. 调度服务重启
2. 消费Pulsar中未ACK的任务消息
3. 从数据库读取任务状态
4. 运行中的任务尝试与执行服务建联
5. 建联成功则继续监控，建联失败则重新调度

**影响范围**：仅调度服务崩溃时，对任务无影响

#### 脑裂处理

**场景**：调度服务与执行服务网络异常，但执行服务实际仍在运行

**解决方案**：
1. 任务提交至执行服务后，执行服务将自己的IP写入任务记录
2. 执行服务处理任务过程中，定时检查任务记录
3. 若发现任务记录中的执行服务IP与自身IP不一致，则终止任务处理

## 四、接口规范

### 4.1 评测工具接口

#### 任务输入约定

**执行命令**：

```bash
evidently run --config ./config.yaml --setting setting.yaml
```

**配置文件**：由执行服务写入槽位目录

#### 任务输出约定

任务输出写入 `./output.json`：

```json
{
    "progress": 100,
    "success": 1,
    "message": null,
    "usages": [
        {
            "judge_id": "ID_LJ001",
            "model_name": "DeepSeek-R1",
            "model_type": "api-openai",
            "input_tokens": 0,
            "output_tokens": 0
        }
    ],
    "report_url": "http://..."
}
```

| 字段 | 类型 | 说明 |
|-----|------|------|
| progress | int | 任务执行进度，0~100 |
| success | int | -1:失败, 0:执行中, 1:完成 |
| message | string | 执行失败时的报错信息 |
| usages | array | Token消耗列表 |
| report_url | string | 评测报告地址 |

### 4.2 产品API接口

#### 任务提交接口

**请求**：`POST /v1/tasks`

```json
{
    "task_id": "model-evaluation-b8sytphze",

    "config": {
        "version": "0.2.0",
        "dataset": "http://...",
        "agents": [...],
        "models": [...],
        "eval": [...]
    }
```

**响应**：

```json
{
    "code": 0,
    "data": {
        "task_id": "model-evaluation-b8sytphze",
        "success": 0,
        "message": ""
    },
    "message": "ok"
}
```

## 五、可观测性

### 性能模型

| 机器规格 | 服务 | 单服务配置 | 单机可部署量 | 并发/吞吐 |

**任务相关**：
- 运行中任务数、等待中任务数、完成任务数、失败任务数
- 任务耗时分布

**三方组件**：
- Pulsar消息发送/消费/确认耗时、错误数
- MongoDB读写耗时、错误数

**对外接口**：
- 提交/查询/取消接口的耗时、响应码统计

**评测容器服务**：
- 执行服务容器数量、使用率统计
