- 执行服务（Executor Service）- Go
- 评测工具集成（astron-eval）- Python CLI

### 1.2 开发约束

| 约束项 | 说明 |
|--------|------|
| **团队配置** | 单人全栈开发 |
| **开发策略** | MVP优先，分层迭代 |
| **依赖服务** | AgentCube、eval-data 已可用 |
| **评测工具** | astron-eval 尚未可用 |

### 1.3 开发策略选择

采用**方案C：MVP骨架分层验证**，原因：
- 单人开发适合小步迭代
- 依赖服务可用但工具未就绪，分层验证可避免阻塞
- MVP闭环后可以更准确地设计后续功能

## 三、质量保障机制

### 3.1 机制诊断

基于 **harness-design** 技能的5维度诊断，各阶段特征如下：

| 阶段 | 复杂度 | 主观性 | 验收清晰度 | 任务时长 | 迭代预期 |
|------|--------|--------|------------|----------|----------|
| 阶段1 | 中等 | 客观 | 清晰 | 中 | 单次 |
| 阶段2 | 中等 | 客观 | 清晰 | 中 | 需打磨 |
| 阶段3 | 复杂 | 半主观 | 清晰 | 长 | 需打磨 |
| 阶段4 | 复杂 | 半主观 | 模糊 | 长 | 需打磨 |
| 阶段5 | 中等 | 半主观 | 模糊 | 中 | 需打磨 |
| 阶段6 | 复杂 | 高主观 | 模糊 | 长 | 持续 |

### 3.2 机制配置

| 阶段 | Planner | Evaluator | Contract | Context Reset |
|------|---------|-----------|----------|---------------|
| 阶段1 | ✓ | ✓ | - | ✓ 阶段结束 |
| 阶段2 | ✓ | ✓ | - | ✓ 阶段结束 |
| 阶段3 | ✓ | ✓ | - | ✓ 每5子任务 |
| 阶段4 | ✓ | ✓ | ✓ | ✓ 每3子任务 |
| 阶段5 | ✓ | ✓ | ✓ | ✓ 阶段结束 |
| 阶段6 | ✓ | ✓ | ✓ | ✓ 每子系统 |

### 3.3 机制定义

#### Planner（任务分解）

**设计原则**：
- 每个阶段分解为可独立验收的子任务
- 子任务边界清晰：一个文件或一个功能点
- 每个子任务有明确的验收标准和验证方式

**执行要求**：
- 阶段开始前输出子任务清单
- 子任务完成后立即标记完成状态
- 阶段结束时核对所有子任务完成情况

#### Evaluator（质量评估）

**评估维度**（适用于所有阶段）：

| 维度 | 评估方式 | 标准 |
|------|----------|------|
| 功能正确性 | 单元测试通过率 | 必须100% |
| 接口符合性 | 对照设计文档检查字段/方法签名 | 必须100% |
| 代码规范 | gofmt/golangci-lint检查 | 必须0警告 |
| 集成验证 | 手动测试记录或集成测试脚本 | 关键路径必过 |

**自我评估校准**：
- 避免"看起来完成了" → 要求有证据（测试输出、日志截图）
- 子任务完成时立即触发评估，不是阶段结束时

#### Sprint Contract（验收协商）

**适用阶段**：验收模糊的阶段（阶段4、5、6）

**协商内容**：
- 阶段开始前明确具体验收项清单
- 用户确认验收项后再开始执行
- 阶段完成时逐项核对

**协商流程**：
```
阶段开始 → 输出验收项清单 → 用户确认 → 执行 → 逐项核对 → 阶段结束
```

#### Context Reset（上下文重置）

**触发时机**：
- 按机制配置的子任务数量触发
- 阶段切换时强制触发
- 发现偏离轨道时触发

**Artifact内容**：
```
当前进度摘要：
- 已完成子任务列表
- 当前子任务状态
- 未解决问题列表
- 下一步计划

关键决策记录：
- 接口设计变更
- 问题解决方案选择
```
